# Test alphabet input on real hardware

## 1. Prerequisites and scope

1. Run after `04-map-the-26-six-dot-alphabet-cells`, before phase 02.
2. This is a user-owned hardware-in-the-loop task.
    1. The agent prepares fresh firmware builds, artifact paths, and flashing instructions from the completed alphabet implementation.
    2. The user flashes the boards, performs the physical checks, and records the results here.
3. Test both baseline keyboards on the pinned ZMK release, using the real `ueb1` alphabet table rather than fixture character rules.
    1. QBF Paintbrushes: Braille keys on the base layer.
    2. Toucan: Braille keys on the layer reached by the braille-mode-key.
    3. Use both halves in their normal split configuration.
4. Use a plain-text editor on macOS with the US input layout; record the host connection and VoiceOver state.
5. This checkpoint covers lowercase letters, chord capture, and access to the Braille layer only.
    1. Do not require Braille-space output, navigation chords, capitals, numbers, punctuation, displays, settings, or persistence.
    2. Use a conventional keyboard to clear the editor or separate test runs when needed.

## 2. Physical checks

1. On each keyboard, enter `abcdefghijklmnopqrstuvwxyz`, using the dot patterns in the preceding alphabet task.
    1. Check every letter against the expected text.
    2. Expect ordinary lowercase characters, not Unicode Braille cells.
    3. Include cross-half chords such as `c` (dots 1, 4) and `x` (dots 1, 3, 4, 6).
2. Enter `aaabbbccc`, then repeat the full alphabet at a comfortable typing pace.
    1. Confirm no missing, duplicated, reordered, or stuck characters.
3. Check release-terminated capture with `c` (dots 1, 4).
    1. Press dot 1, add dot 4, and hold both for at least two seconds: expect no output.
    2. Release dot 1 while dot 4 remains held: expect no output.
    3. Release dot 4: expect exactly one `c`.
    4. Repeat with the press and release order reversed: expect the same result.
    5. Repeat while releasing and re-pressing dot 1 with dot 4 still held: expect only one `c` after the final release.
4. Check a key joining a partly released chord.
    1. Press dots 1 and 4, release dot 1, then add dot 5 while dot 4 is still held.
    2. Release the remaining keys: expect exactly one `d` (dots 1, 4, 5), with nothing emitted earlier.
5. On Toucan, exercise both ways of reaching the Braille layer.
    1. Hold the mode key while entering letters; each letter must appear after its final dot release, without waiting for the mode key to be released.
    2. Tap the mode key to switch layers, enter letters, then return with the configured return-layer key.
    3. Confirm the mode key does not contribute a chord bit and conventional typing works after returning.

## 3. Result and acceptance

1. Record the module, keyboard configuration, and ZMK revisions, firmware artifact paths, and the keyboard tested.
2. Record expected and actual output and pass/fail results for each check on each keyboard.
3. For a failure, include the exact dot press/release sequence and whether it reproduces; attach a text capture, log, or video where useful.
4. Pass when all 26 letters and the timing, repeat, split, and layer-access checks succeed on both keyboards without missing, duplicated, premature, or unintended host output.
5. Report failures against this alphabet checkpoint rather than waiting for later features; record any unavailable hardware explicitly instead of treating an untested board as passed.
